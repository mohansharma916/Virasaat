Changes cover the Expo mobile app, NestJS API, public website, and deployment configuration. They are local changes awaiting review and deployment. No production database migration, deployment, real email send, or store transaction was performed. Actual environment files were left unchanged.

## Before deploying these changes

1. Back up the existing PostgreSQL database and retain encryption keys. The checked-in migrations are upgrades: they require an existing baseline schema and cannot initialize an empty database.
2. Preserve any older LOCAL ciphertext at `PRIVATE_STORAGE_DIR`, or migrate it to S3 before replacing the old API container. Compose currently has no persistent mount for that legacy directory. Replacing its only copy would lose those files.
3. Run migrations before starting the updated API. The workflow runs them in this order; they can also be run from `virasat-server` with the appropriate environment:

   ```sh
   npm run db:migrate:prd21
   npm run db:migrate:subscriptions
   npm run db:migrate:auth-security
   npm run db:migrate:vault-check-in
   ```

   The timestamp migration interprets old event timestamps as UTC and preserves existing pending due instants. Validate that assumption against a restored database before production rollout. No live migration was tested here.
4. Review the new settings documented in `virasat-server/.env.example`. Keep `NODE_ENV=production` and schema synchronization disabled. Configure a bounded `TRUST_PROXY` value only for the real proxy topology so IP limits identify clients correctly. Set real SMTP and S3 access; IAM roles can supply S3 credentials without static keys.
5. Preserve the key that encrypted existing `v1` records. To rotate, choose a new current version/key and retain old keys in `ENCRYPTION_MASTER_KEYS` until all dependent records and backups have been migrated. This change supports historical key lookup; it does not automatically re-encrypt old content or provide an operational disaster-recovery service.
6. Rebuild the native app because dependencies, including file sharing, changed. Test Google login, biometric enrollment/unlock/backgrounding, password recovery, saved-file sharing, video recording, and upload cancellation on physical Android/iOS devices. Verify the website dialog with keyboard and assistive technology.

Existing JWTs without a session version require signing in again. Logout revokes **all** sessions for the account. Existing paid records without provider-verification evidence retain their audit information but receive Starter access until real store verification exists. Offline logout clears the device but cannot contact the server to revoke other copies of a token.

## Remaining work

Real store billing/reconciliation, durable reminder/escalation jobs, invitations and acceptance, verified recipient release, and account deletion remain unavailable. These need complete backend workflows and end-to-end validation before enabling them. Website terms/company/contact details still require owner review.

Mobile dependencies were updated within Expo SDK 57 compatibility. The critical advisory and patched decoder/UUID advisories were removed. The decoder uses the upstream MIT-licensed 0.5.0 algorithm with only a CommonJS export adaptation; `vendor/decode-uri-component/README.md` documents maintenance and removal. The local package and `install-links=true` configuration are included in the lockfile and verified by clean installation.

The final clean-install production-dependency audit reports **19 high, 0 moderate, and 0 critical** package flags, down from 34 total including one critical. The remaining chains originate from [braces](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) and [node-forge](https://github.com/advisories/GHSA-86w9-cpqp-85rv), for which the reviewed advisories list no patched release. They include Expo/build tooling classified as production dependencies; the audit count does not establish independently exploitable runtime defects. Do not apply npm's suggested incompatible Expo/React Native downgrades to remove those flags. Monitor supported upstream patches.

The Expo web token adapter still uses localStorage. A public browser vault needs a separately reviewed authentication/storage design. Durable draft recovery after process death also remains a product improvement; current in-memory upload request keys do not survive an app restart.
